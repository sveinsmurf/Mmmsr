is the COLO replication path itself, not btrfs.

## Phase 2: the secondary's disk path

### Cache modes (query-named-block-nodes)

All nodes on both hosts report the same settings:

```
cache.no-flush=False, direct=False, writeback=True, discard=None
```

So every layer (primary quorum child, NBD export, secondary active and
hidden disks) uses `cache=writeback` with `direct=off`. Flushes do reach
the host, but not synchronously through the secondary's write path.

### Link latency

```
ping over direct link (.104→.105): 50/50 received,
rtt min/avg/max/mdev = 0.118/0.226/0.592/0.081 ms
```

iperf3 over direct link: 911 Mbit/s. The link is not the bottleneck.

### Secondary disk behaviour while T1 runs on .105

iostat -x on `.105` while the guest is running fio (3 samples):

| sample | w/s | wkB/s | w_await (ms) | %util |
|--------|-----|-------|--------------|-------|
| 1 | 68 | 1364 | 14.28 | 88.7% |
| 2 | 73 | 1836 | 14.10 | 89.0% |
| 3 | 49 | 752 | 13.14 | 65.0% |

The secondary disk is not idle: it is doing 50–70 writes/s at ~14 ms
each, with utilisation 65–89%. That is the same write load as T1 in the
guest. The HDD is spending most of its time servicing the replicated
writes and flushes.

### Checkpoint interval

Setting `x-checkpoint-delay` from 500 ms to 2000 ms did not change the
T1 result:

| checkpoint delay | IOPS | fsync mean | fsync p99 |
|------------------|------|-----------|-----------|
| 500 ms | 1.0–1.7 | 443–661 ms | 1028–1233 ms |
| 2000 ms | 1.7 | 437.81 ms | 1283.5 ms |

The cost is per write, not per checkpoint, as expected. Checkpoint delay
restored to 500 ms after the test.

### Dirty rate

QEMU dirty-rate sampling (page-sampling mode) during a quiet period with
FerrumC running: 1–2 pages/s (essentially idle). This is a quiescent
measurement; the actual generation bursts from earlier were much larger
but are no longer running. Dirty-rate was not a limiting factor during
the T1 test.

### Phase 2 conclusion

The bottleneck is the secondary's HDD: every replicated write plus fsync
lands on `.105`'s `/dev/sda`, which has ~14 ms write latency under this
workload. The write path through COLO's replication (per-write fsync to
the secondary) is the cause. It is not btrfs, not the link, and not the
checkpoint interval.

### Diagnostic: secondary disks on tmpfs

The secondary's `secondary-active.qcow2` and `secondary-hidden.qcow2`
were moved to a 3 GiB tmpfs on `.105` (symlinked from the normal path)
and the pair was restarted. The guest rebooted (fresh `setup + start`),
so this run's numbers are not directly comparable to the earlier COLO
runs, but the relative change is meaningful.

| test | IOPS | fsync mean | fsync p99 | T2 |
|------|------|-----------|-----------|----|
| T1 run 1 (secondary tmpfs) | 9.6 | 101.07 ms | 295.7 ms | — |
| T1 run 2 (secondary tmpfs) | (test hung > 10 min; aborted) | — | — | — |
| T2 (secondary tmpfs) | — | — | — | 67.2 MB/s |

T1 improved from 1.0–1.7 IOPS / 443–661 ms fsync to 9.6 IOPS / 101 ms
fsync (still not great, because the primary's HDD is also in the path).
T2 went from 19.6–28.5 MB/s to 67.2 MB/s (similar to standalone 75.6 MB/s).

During the second T1 run the primary QEMU **segfaulted**:

```
qemu-system-x86[17745]: segfault at 90 ip 0000555cb60400e1 ...
```

The tmpfs-symlink setup is not a stable configuration (QEMU follows the
symlink for the NBD target and the mirror job, and the file was replaced
from underneath it during the resync). The disks were moved back to the
normal HDD path and the pair was restored.

**Conclusion: the HDD on the secondary is the dominant factor. Even
partially removing it (active/hidden on tmpfs, base image still on HDD)
roughly halved the fsync latency and brought sequential writes back to
standalone speed. A production configuration should put the secondary's
replication disks on a faster device (SSD or NVMe), not tmpfs.**
