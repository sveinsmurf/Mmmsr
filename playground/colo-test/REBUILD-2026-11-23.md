# COLO Guest Rebuild — 2026-11-23

This is a fresh rebuild after the guest root filesystem (btrfs) became
corrupted during COLO replication. The original `base.qcow2` was moved aside
and a new guest image was built from a fresh Arch cloud image.

## Why rebuild

The guest `.110` showed these symptoms for ~1 hour:

- SSH (port 22) refused even though the seed had `sshd` enabled.
- FerrumC and the dashboard listened on 25565/9000 but the Minecraft status
  ping timed out.
- Console login rejected every password, including one set directly in the
  image.
- Serial log showed BTRFS errors (`open_ctree failed: -5`) and a failed
  `/sysroot` mount during initrd.

The root cause is the same btrfs corruption documented in `COLO-TEST.md`:
replication interrupted the btrfs metadata and the filesystem came back
inconsistent. `btrfs` is too fragile for this COLO lab, so the new guest uses
**ext4**.

## Lab policy for this proof of concept

This guest is **local LAN only** (`192.168.35.0/24`, not exposed to the
internet). To keep the proof of concept simple:

- no firewall rules (iptables/nftables left empty/default-accept)
- no SELinux/AppArmor or other sandboxing
- SSH password auth enabled for user `svein`

Security hardening is intentionally deferred until the COLO concept works.

## Steps performed

1. Stopped both QEMUs with `tools/colo.py cleanup`.
2. Moved the corrupted `base.qcow2` aside on `.104`
   (`/mnt/vms/colo-primary/base.qcow2.corrupt.<timestamp>`).
3. Downloaded a fresh Arch Linux cloud image on `.104` and resized it to 10G.
4. Mounted the new image via `qemu-nbd` and confirmed the root partition is
   `nbd0p3` (btrfs).
5. Copied the full root tree into `/tmp/guest-new` to prepare for the ext4
   conversion (the copy is complete; ~1.6 GiB of data).

## Conversion: btrfs -> ext4

6. Unmounted everything, reformatted `nbd0p3` as **ext4** (label `root`),
   and restored the copied data.
7. Wrote a new `/etc/fstab` with the ext4 UUID for `/` and the vfat UUID
   for `/efi` (the old btrfs subvolume line was removed).
8. Removed `rootflags=compress=zstd:1` from `GRUB_CMDLINE_LINUX_DEFAULT`
   (that is a btrfs-only flag).
9. Regenerated `grub.cfg` in the chroot; the new entry uses
   `root=UUID=f981db21-3816-4898-8e4b-f0c8d69883a4 rw`.

## GRUB "unknown filesystem" fix

The first boot after the conversion showed `grub_fs_probe:122:unknown
filesystem` and dropped to a `grub rescue>` prompt. The BIOS-installed
GRUB in the MBR still had only btrfs modules embedded. Reinstalling GRUB
fixed it:

```sh
chroot /mnt/guest-root grub-install --target=i386-pc /dev/nbd0
grub-mkconfig -o /boot/grub/grub.cfg
```

After that the guest booted normally from the ext4 root.

## User setup

The fresh cloud image ships without the `svein` user, and cloud-init's
`passwd` field is ignored for existing users (with `lock_passwd: true`
default it even locks the password). To avoid all of that, the user was
created directly in the image:

```sh
useradd -m -s /bin/bash -G wheel svein
echo 'svein:123454321' | chpasswd
echo 'svein ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/svein
```

SSH host keys were regenerated inside the image with `ssh-keygen -A`
(the old ones were zero bytes, which is why sshd previously failed with
"no hostkeys available"). Firewall services (`iptables`, `nftables`,
`firewalld`) were disabled and masked.

FerrumC was copied into `/home/svein/ferrumc/` (binary, `configs/`,
`world/`, `logs/`, `whitelist.txt`) and a `ferrumc.service` systemd unit
was created and enabled. The seed's cloud-init `runcmd` also sets the
password via `chpasswd` and enables `sshd` on every boot, so this works
even if the image is rebuilt from scratch later.

## COLO disk I/O bottleneck

With COLO active (500 ms checkpoint interval), direct disk writes inside
the guest measured **~3.1 MB/s**. FerrumC's world generation stalled for
15+ minutes in uninterruptible I/O (`D` state, `rq_qos` wait).

The guest was taken out of COLO by killing the secondary on `.105` and
running the documented primary-failover sequence on `.104`
(`x-blockdev-change`, `blockdev-del`, object deletions,
`x-colo-lost-heartbeat`, `cont`). Standalone, the same write test measured
**~462 MB/s**.

FerrumC then completed world generation in 9m 39s and the server came up
on 25565/9000. Once the world is generated, normal play should have much
better I/O because COLO only needs to forward writes, not bulk-generate.

## Minecraft protocol mismatch

Early status ping attempts used protocol 754 (Minecraft 1.20.1) and timed
out. The installed FerrumC speaks protocol **772 (Minecraft 1.21.8)**.
With the right protocol version the status ping returns:

```json
{"version":{"name":"1.21.8","protocol":772},
 "players":{"max":100,"online":1,
            "sample":[{"name":"Sveinsmurf","id":"3a717427-..."}]}}
```

The `Unhandled handshake error: Connection Dropped` spam in the journal
was the client retrying while world generation was still running.
